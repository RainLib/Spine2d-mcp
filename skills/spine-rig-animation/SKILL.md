# Spine 骨架与动画制作

将已确认的素材和动作意图落实为可编辑的 Spine 工程及经过验证的运行数据。骨架结构、部件数量、动画名单和预算按当前任务确定；不要从其他游戏复制默认角色规则。

## 确认当前能力与输入

读取现有 Spine JSON／工程版本、素材交接记录及项目实际运行时。发现当前会话的 MCP 工具并读 schema；工具源码存在不代表当前连接已刷新。按 [MCP 与本地扩展](references/pipeline-operations.md) 选择已实现的操作。

需要继续分层或对齐时，使用已安装的 `spine-asset-prep`；没有该技能时直接检查已有工程和交接记录。不要为单独调整动画而重新生成或拆分素材。

源文件与暂存分离。需要原生导出时先暂存 JSON 和全部引用图片。保持用户已授权的工作范围，直接完成可逆编辑和验证；不要增加每一步都重新确认的审批流程。

## 骨架、网格与权重

先确定根节点、角色位移、身体控制、肢体链、附属物和挂点的职责。父子关系须符合运动隔离需求；约束目标、顺序和皮肤依赖应可解析。补骨或重排骨骼时同步处理索引引用，不能只改 bones 数组。

按画面表达和动作范围选择连续主体及必要的独立表面，保留正确遮挡。网格密度服务于关节弯曲和轮廓，避免无效透明三角形与细长易翻面的三角形。用实际顶点、影响数和同时可见附件衡量成本，不把总附件数当作画面碎片数。

脸、硬壳、道具等需要刚性时约束其影响骨骼；柔性关节保留有限过渡。披风等隔离区域同时检查直接权重、祖先骨骼、约束和 Deform。不要把 Weights Lock 当成动画隔离或绑定补偿。

具体检查和编辑边界见 [Mesh 与权重](references/mesh-weights.md)。能力不足时把通用算法作为显式局部扩展实现并验证，不硬编码角色名到核心，也不绕过拒绝条件静默损坏 Deform／linked mesh。

## 动作和物理效果

先从用户描述与游戏契约提取可观察要求：动作读得清、接触点对齐、承重成立、轮廓不塌、首尾可接、取消后能恢复。仅制作本次需要的待机、移动、蓄力、释放、收势、受击、退场或阶段动作，沿用已有命名接口。

动画应驱动真实骨架和附件。导出动态预览时使用实际 Spine 播放；相机平移缩放或静态图片不能作为绑定、物理、循环质量的通过证据。采样完整动作、关键接触瞬间和状态衔接，核对网格翻折、脚漂移、面部变形、挂点漂移及循环跳变。

需要头发、布料、尾巴等物理次级运动时读取 [动画与物理验证](references/motion-physics.md)。选择运行时物理还是已制作的确定性动作须符合目标；不把正弦摆动或普通关键帧声称为已实现 Spine Physics。

## 输出与验证层次

保留可编辑 `.spine`（本机导入／保存能力可用时）、JSON、atlas 全部页、纹理和动作预览。报告绑定实际输出哈希及编辑器／运行时版本。

区分已完成的结构检查、原生导入、运行时加载、完整动作采样和视觉验收。`godot_validate` 只提供独立项目的加载及短采样，不自动完成动作质量与游戏验收。没有原生工具时完成当前可执行部分，明确尚未验证的结果，不凭 JSON 合法就称为制作完成。

后续需要游戏挂点、换肤或装备接入时，使用可用的 `spine-game-integration`，交接实际动画、skin／slot／attachment 契约。
